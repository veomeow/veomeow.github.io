## fuzzing이란

퍼징(fuzzing)이란, 프로그램이나 시스템에 다양한 데이터를 반복적으로 입력하여 프로그램이 의도하지 않은 동작이나 에러, 충돌, 메모리 오류 등을 찾아내는 소프트웨어 테스트 기법입니다.

퍼징을 통해 Buffer Overflow, Use-After-Free 등의 메모리 오류나 프로그램의 비정상 종료 등을 탐지할 수 있습니다.

### fuzzing 동작 과정

퍼징은 일반적으로 다음과 같은 과정을 반복합니다.

1. **초기 입력값 준비** : 테스트에 사용할 초기 데이터(Seed)를 준비
2. **입력값 생성 및 변형** : 기존 데이터를 변형하거나 새로운 데이터 생성
3. **프로그램 실행** : 생성한 입력값을 테스트 대상에 전달
4. **결과 확인** : 프로그램의 충돌, 오류, 실행 정보 등을 확인
5. **반복** : 유의미한 입력값을 저장하고 다음 테스트에 활용

이때 퍼징에 사용되는 입력 데이터의 집합을 **Corpus**라고 합니다.

모든 퍼저가 동일한 방식으로 동작하는 것은 아니며, 일부 퍼저는 프로그램의 실행 결과를 활용하여 다음 입력값을 개선하기도 합니다.

### fuzzing 종류

퍼징의 종류는 입력값 생성 방식과 프로그램 내부 정보에 대해 아는 정도에 따라 구분할 수 있습니다.

#### 입력값 생성 방식

퍼징은 입력값 생성 방식을 기준으로 크게 두 가지로 구분할 수 있습니다.

**Mutation-based fuzzing**

: 기존 입력 데이터(seed)를 기반으로 데이터를 변형하여 새로운 테스트 케이스를 생성하는 방식

기존 데이터의 일부 비트를 변경하거나 데이터를 추가·삭제하는 등의 방법을 사용합니다.

입력 형식에 대한 정보 없이도 사용할 수 있지만, 데이터가 손상되면 프로그램의 입력 검증 단계에서 거부될 수 있습니다.

**Generation-based fuzzing**

: 입력 포맷의 구조와 규칙을 바탕으로 새로운 테스트 케이스를 생성하는 방식

예를 들어 JSON을 처리하는 프로그램이라면 JSON 문법을 기반으로 다양한 필드와 값을 생성할 수 있습니다.

입력 형식에 대한 정보가 필요하지만, 복잡한 구조의 데이터를 생성하는 데 유용합니다.

#### 프로그램 내부 정보 사용 방식

퍼징은 프로그램 내부 정보 사용 방식을 기준으로 블랙박스 퍼징, 화이트박스 퍼징, 그레이박스 퍼징으로 구분할 수 있습니다.

- **Black-box fuzzing** : 타겟 프로그램의 내부 실행 정보를 활용하지 않고 입력과 실행 결과만을 이용하는 방식
- **White-box fuzzing** : 타겟 프로그램의 내부 구조와 실행 조건을 분석하여 입력값을 생성하는 방식
- **Gray-box fuzzing** : 타겟 프로그램의 내부 정보를 일부 활용하는 방식으로, 주로 코드 커버리지 등을 이용하여 새로운 실행 경로를 탐색하는 방식

Gray-box Fuzzing에서 대표적으로 활용하는 기법이 **Coverage-guided Fuzzing**입니다.

코드 커버리지(Code Coverage)는 테스트 과정에서 프로그램의 어느 부분이 실행되었는지를 나타내는 정보입니다.

Coverage-guided Fuzzing은 이러한 정보를 활용하여 이전에 실행되지 않았던 코드 영역이나 실행 경로를 발견한 입력값을 저장하고, 이를 바탕으로 다음 테스트를 진행합니다.

즉, 단순히 무작위 데이터를 입력하는 것이 아니라 이전 테스트에서 얻은 정보를 다음 테스트에 활용하는 방식입니다.

## fuzzer란

퍼저(fuzzer)란 퍼징을 자동으로 수행하는 도구입니다.

퍼저마다 입력값을 생성하는 방식과 실행 정보를 수집하는 방법, 주요 테스트 대상 등이 다릅니다.

이번에는 테스트 대상과 퍼징 방식의 차이를 기준으로 AFL++, boofuzz, libFuzzer, syzkaller를 선정하였습니다.

### fuzzer의 종류와 차이점

#### AFL++

AFL++(American Fuzzy Lop Plus Plus)는 기존 AFL을 확장한 Coverage-guided Fuzzer입니다.

기존 입력값을 변형하여 프로그램에 전달하고, 코드 커버리지를 이용하여 새로운 실행 경로를 탐색합니다.

AFL++는 실행 정보를 수집하기 위해 계측(Instrumentation)을 사용합니다.

계측이란 프로그램의 실행 과정에서 어떤 코드가 실행되었는지 등의 정보를 수집하도록 하는 작업입니다.

소스 코드가 있다면 LLVM, GCC 등을 통해 계측을 적용할 수 있고, 소스 코드가 없는 바이너리도 QEMU나 Frida 등을 활용하여 계측할 수 있습니다.

또한 AFL++는 Forkserver와 Persistent Mode를 지원합니다.

- **Forkserver** : `fork()`를 이용하여 자식 프로세스를 생성하고, 매번 프로그램을 처음부터 실행하는 비용을 줄이는 방식
- **Persistent Mode** : 하나의 프로세스에서 여러 입력값을 반복 처리하는 방식

따라서 AFL++는 소스 코드가 있는 프로그램뿐만 아니라 바이너리에도 활용할 수 있으며, 다양한 계측 및 실행 방식을 지원한다는 특징이 있습니다.

#### boofuzz

boofuzz는 네트워크 프로토콜을 대상으로 하는 퍼징 프레임워크입니다.

프로토콜 메시지의 구조를 정의하고, 각 필드를 변형하여 테스트 케이스를 생성하는 방식으로 동작합니다.

boofuzz는 메시지를 다음과 같은 요소로 구성합니다.

- **Request** : 하나의 프로토콜 메시지
- **Block** : 메시지를 구성하는 데이터 영역
- **Primitive** : 문자열, 숫자 등의 개별 데이터 요소

예를 들어 HTTP 요청을 테스트한다면 요청 메서드, URI, 헤더 등의 필드를 정의하고 특정 필드의 값을 변경하여 테스트할 수 있습니다.

전체 데이터를 무작위로 변형하는 대신 프로토콜의 구조를 고려하여 입력값을 생성하고 변형한다는 점이 특징입니다.

또한 여러 요청의 실행 순서를 정의할 수 있어, 이전 요청의 결과에 따라 다음 동작이 달라지는 프로토콜도 테스트할 수 있습니다.

boofuzz는 구조 기반 입력 생성과 Mutation을 결합하며, 일반적으로 내부 코드 커버리지 없이 네트워크 응답이나 타겟의 상태를 관찰하는 Black-box 방식으로 사용됩니다.

#### libFuzzer

libFuzzer는 LLVM에서 제공하는 In-process Coverage-guided Fuzzer입니다.

AFL++와 마찬가지로 코드 커버리지를 활용하지만, 퍼저와 타겟 코드가 같은 프로세스에서 실행된다는 점이 특징입니다.

libFuzzer는 일반적으로 `LLVMFuzzerTestOneInput()` 함수를 통해 입력값을 전달합니다.

다음은 LLVM 공식 문서에서 제공하는 예제 코드입니다.

```cpp
#include <stdint.h>
#include <stddef.h>

extern "C" int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
  if (size > 0 && data[0] == 'H')
    if (size > 1 && data[1] == 'I')
      if (size > 2 && data[2] == '!')
        __builtin_trap();
  return 0;
}
```

출처 : https://llvm.org/docs/LibFuzzer.html

위 코드는 입력값의 처음 3바이트가 `HI!`일 때 `__builtin_trap()`을 실행하는 예제입니다. (HI!asdf여도 실행함.)

libFuzzer는 다양한 입력값을 전달하여 해당 조건에 도달하는지 테스트합니다. 이 코드는 퍼징 동작을 보여주기 위한 예제이며, 실제 취약점이 포함된 코드는 아닙니다.

이처럼 퍼저가 생성한 입력값을 테스트 대상에 전달하는 코드를 **Harness**라고 합니다.

libFuzzer는 Harness를 반복 호출하므로 테스트마다 별도의 프로세스를 생성할 필요가 없습니다.

다만 같은 프로세스에서 여러 입력값을 처리하므로 이전 테스트에서 변경된 상태가 다음 테스트에 영향을 주지 않도록 주의해야 합니다.

#### syzkaller

syzkaller는 운영체제 커널을 대상으로 하는 Coverage-guided Fuzzer입니다.

일반적인 프로그램에 파일이나 문자열을 입력하는 것과 달리, System Call을 조합하여 커널의 동작을 테스트합니다.

예를 들어 파일을 읽으려면 `open()`으로 파일을 열어 유효한 파일 디스크립터를 얻은 후 `read()`를 호출해야 합니다.

이처럼 시스템 콜 사이에는 호출 순서와 자원 의존성이 존재하기 때문에, 커널 퍼징에서는 단순히 인자 값을 변형하는 것뿐만 아니라 시스템 콜 간의 관계도 고려해야 합니다.

syzkaller는 `syzlang`이라는 기술 언어를 사용하여 시스템 콜의 인자와 자원 관계 등을 정의합니다. 이를 바탕으로 여러 시스템 콜의 호출 순서를 구성하고 변형하여 테스트를 수행합니다.

또한 Linux에서는 KCOV를 활용하여 커널의 코드 커버리지를 수집합니다.

KCOV는 커널의 코드 커버리지 정보를 사용자 공간에 제공하는 기능으로, syzkaller는 이를 활용하여 새로운 실행 경로를 탐색합니다.

따라서 syzkaller는 시스템 콜의 구조와 호출 순서, 자원 관계 등을 고려하여 커널을 퍼징한다는 특징이 있습니다.

### fuzzer 비교

| Fuzzer | 주요 대상 | 입력값 생성 방식 | 내부 정보 활용 |
| --- | --- | --- | --- |
| AFL++ | 프로그램 및 바이너리 | Mutation 중심 | Gray-box |
| boofuzz | 네트워크 프로토콜 | 구조 기반 생성·변형 | 주로 Black-box |
| libFuzzer | 함수 및 라이브러리 | Mutation 중심 | Gray-box |
| syzkaller | 운영체제 커널 | 시스템 콜 기반 생성·변형 | Gray-box |

AFL++와 libFuzzer는 모두 코드 커버리지를 활용하지만, 실행 방식에 차이가 있습니다.

AFL++는 Forkserver를 이용하여 자식 프로세스에서 테스트를 수행할 수 있고, libFuzzer는 타겟 함수를 동일한 프로세스 내부에서 반복적으로 호출합니다.

반면 boofuzz는 네트워크 요청을 전송하고 응답이나 연결 상태 등을 확인하며, syzkaller는 시스템 콜을 조합하여 커널의 동작을 테스트합니다.

즉, 퍼저마다 테스트 대상뿐만 아니라 입력값을 전달하고 실행 결과를 확인하는 방식에도 차이가 있습니다.

#### In-process & Persistent Mode

퍼저의 실행 방식을 살펴보면서 In-process와 Persistent Mode의 차이가 헷갈려서 정리해봤습니다.

- **In-process** : 퍼저의 테스트 실행 코드와 타겟 코드가 동일한 프로세스에서 실행되는 방식
- **Out-of-process** : 퍼저와 타겟이 별도의 프로세스에서 실행되는 방식
- **Persistent Mode** : 타겟 프로세스를 재사용하여 여러 입력값을 반복 처리하는 방식

In-process는 실행 위치, Persistent Mode는 프로세스 재사용 여부에 대한 개념이었습니다!

## 정리

퍼징은 단순히 무작위 데이터를 반복 입력하는 것이 아니라, 입력 데이터의 구조나 코드 커버리지 등의 정보를 활용하여 테스트를 수행할 수 있다는 것을 알게 되었습니다.

또한 퍼저마다 테스트 대상이 프로그램, 네트워크 프로토콜, 운영체제 커널 등 다양하다는 것을 알 수 있었습니다. 이렇게 테스트 대상이 다르기 때문에 입력값을 생성하거나 전달하는 방식에도 차이가 있었습니다.

특히 syzkaller를 통해 커널 퍼징에서는 시스템 콜의 인자뿐만 아니라 호출 순서와 자원 관계도 중요하다는 점을 알게 되었습니다. 개인적으로 커널에서 일어나는 일에 관심이 있어서 syzkaller를 조사할 때 어렵긴 했지만 재밌었습니다!!
